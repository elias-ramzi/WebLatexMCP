# Tools

All tools take an optional `project` id (defaults to `WEB_LATEX_MCP_DEFAULT_PROJECT`). File paths are always
POSIX (`/`-separated), on every OS. That covers the project-relative paths you pass and get back, and the
absolute ones returned by `compile` (`pdfPath`, `logPath`), `render_pages` (`pdfPath`, `outDir`, each
page's `pngPath`), `pdf_geometry` (`pdfPath`), `extract_text` (`pdfPath`), `register_project` (`path`), `project_sync` (`path`),
`list_projects` (`path`), and the directories `doctor` names inside its check details — in the result
**text** as well as in `structuredContent`, so a single result never spells one path two ways. `compile`'s `pdfUrl` is not a path at all — it is a `file://` URL, built from the path as the
filesystem spells it.

| `register_project`       | Register a project and **persist** it to the workspace, so it survives a restart and is picked up by other sessions — no `WEB_LATEX_MCP_PROJECTS` needed. Pass `gitUrl` for a git project (cloned immediately unless `clone: false`) — the intended path for Claude Desktop: just paste your Overleaf git URL in the chat. Pass `path` instead for a **local** project: something already on this machine, compiled and edited in place with no clone — a directory, or **a file inside it** (`~/proposals/eurohpc.md`, `paper/main.tex`), in which case the folder holding it is registered and a `.tex` named that way also becomes the `rootFile` (see [Local projects](#local-in-place-projects)). Exactly one of the two. The project id names a directory, so it is refused only where that is unsafe or could be mistaken for another id — a path separator or another character a Windows file name cannot hold, a backtick, a control, bidirectional-override or invisible character (a zero-width space, a variation selector, …), a space other than U+0020, a line or paragraph separator, a leading combining mark, text that is not NFC-normalised, a leading `.` or `-`, leading or trailing whitespace, a trailing `.`, a Windows device name, `registry.json` or a `*.pdf` name, `~` followed by a digit, `__proto__`/`constructor`/`prototype`, or more than 64 characters (or 246 UTF-8 bytes) — and so is a new id that differs from an existing one only in letter case; Unicode letters, spaces and punctuation are fine (`thèse`, `My Thesis`) — see [Configuration → Project ids](configuration.md#project-ids) for the whole rule. A secret embedded in an http(s) `gitUrl` is removed before anything is stored, echoed or cloned — `user:token@` keeps `user@`, and a token used as the username is removed whole — and the result says what was removed; supply a token with `set_credential` or `tokenEnv` instead. A directory another project already uses is refused. See [Registering a project from the chat](#registering-a-project-from-the-chat). Pass `default: true` to make it the project used when a call omits `project` — applied now and persisted; `WEB_LATEX_MCP_DEFAULT_PROJECT`, when set, always wins. | `render_pages`           | Rasterize the compiled pages to PNG **so the model can see the layout**, and return them inlined as image content plus their file paths. Takes `pages`, or **`labels`** in place of them — because after moving a float its page is exactly what is unknown, and the question is never "page 8" but "the page the table I just restructured landed on". Labels resolve through the build-dir `.aux` of the **last compile**, so a label added since (or one whose reference has not converged — LaTeX's "may have changed, rerun") is not yet there; the result echoes the `label -> page` mapping it used, so you can see what it actually rendered. `labels` and `pages` together are rejected rather than one silently winning. **A label is refused, never guessed at.** The `.aux` records the _printed_ page; turning that into a PDF page index goes through the PDF's own **`/PageLabels`** tree when the document has one (`hyperref` writes one), so roman front matter, `\frontmatter` and an appendix scheme all resolve **exactly** rather than being refused. Two refusals belong to that path: a printed page the tree prints on **no** page is reported as a stale `.aux` (the label is defined — the page moved), and one it prints on **several** pages (a restarted `\pagenumbering`) is refused with every candidate named, never resolved to the first. A PDF with **no** `/PageLabels` — the usual `article` without `hyperref` — falls back to the printed page as the index, but only once **that PDF page's own folio reads the printed page**, and a neighbouring page's folio reads the adjacent number (and the last page reads as no decimal number other than the page count — a restart that never goes down leaves it reading something else; a last page with no folio or a roman one passes, and one that could not be read refuses) — the page number in its footer, or at the edge of its running head (a section number or a table cell can pass for a folio on one page; a folio continues on the next): a title page or a `\setcounter{page}` shifts every page while leaving each printed number plausible, so a label whose candidate page shows another folio, no folio at all (a title page, `\pagestyle{empty}`), a running head that reads as two different numbers, a folio no neighbouring page corroborates, or that points past the end of the PDF is refused (`unverifiedPage`), and the refusal says which. A one-page PDF needs no neighbour: its only page is the only one a label can be on. A foot in one of the common forms — `Page N`, `N of M`, `Page N of M`, `N/M`, `– N –` — is read as the folio and wins over the running head. A document whose arabic numbering restarts (a printed page that goes down in `.aux` order, such as a supplement after `\setcounter{page}{1}`) has every label refused on this route (`restarted`). A **beamer** deck's `/PageLabels` tree is never used: it numbers frames, which every overlay slide of a `\pause` frame repeats, while `\label` records the slide, and `pgfpages` layouts make even a "1".."N" tree prove nothing (`2 on 1` puts two slides on a sheet; `resize to` shifts every label one slide late), so a deck takes this folio route: a footline printing the slide number (`\insertpagenumber`) confirms the page, and a deck without one is refused — and before that, a label whose printed page disagrees with beamer's own record of its slide (`\beamer@slide`, in the same `.aux`) is refused (`slideMismatch`): a `resize to` deck printing `\insertpagenumber` (each sheet shows its true slide, the label the next one) is refused as `pgfpagesLayout` before that, so this record adds a second check to a deck whose build records show no pgfpages. A key holding one level of braces (`fig:{a}`) is checked like any other; a label in an `allowframebreaks` frame disagrees with that record too and is refused although its page was right. The folio is read from the text layer, not a page box, so this route is evidence rather than proof, and a few shapes still pass it wrongly **whenever the `.log`'s shipout record below is not used** — it is used only when its marks number exactly the PDF's pages, so it is skipped when the log cannot be read, when the document writes text that looks like a mark (`\message{[3]}`), or when a mark is cut in a way the parser will not guess at: a shifted document whose foot is empty with a `[b]` table on consecutive pages whose last cell equals the PDF page index; a head showing section numbers that advance one per page, beside a foot form outside the list (`Draft 3`, `p. 3`); and an arabic restart with no label on any page before it. On **both** routes a resolved page is then checked against the `.log`'s **shipout record** — the page counter TeX writes there (`[1] [2] …`) as it ships each page out — and refused (`unverifiedPage`) unless that PDF page was shipped with the label's decimal printed page as its counter and, on the folio route, no other page shipped with that counter could print the same number: another page shipped with it passes only when its own text shows a page number in another style — a roman numeral, a letter, or a prefixed number such as `S1` — which is what an appendix under `\pagenumbering{alph}` or `{Roman}`, or a supplement under `S\arabic{page}`, prints after resetting the counter; one showing no number, two readings or any decimal number counts as a second copy. The record can only refuse a page, never choose one (a document can write text that looks like it), and the check is skipped when its marks do not number exactly the PDF's pages. An extra mark and a missed one in the same log can line up to the right count and shift the record, which can refuse a correct label or miss a refusal (never worse than the route's own answer); a counter restarted for back matter that prints no page number (`\pagestyle{empty}`, `\pagenumbering{gobble}`) refuses the body labels sharing those counters on this route; and whatever stands where a folio is looked for on such a page and reads as a page number in another style — a section number opening it (`A`, `S1` above an empty foot), or a whole last line such as an axis label `x`, a two-letter word, or `mix` read as a roman numeral — can let a repeated counter through, leaving the route's own answer as it was without the log. It errs the other way too: a last page that prints no folio but opens with a section heading (whose number is read from the head), or an appended `\includepdf` page with its own folio, refuses every label although nothing restarted — the refusal says the last page reads as another number, a restart or a different number on that page, without claiming which. Load `hyperref` for an exact lookup. The label's own number is not consulted — in an `article` its digits turn up on nearly every page — so a label that has none resolves like any other. A non-decimal printed page (`iv`, `A-3`) is refused there too, and so is an _arabic_ label in a document where any label prints roman. On either route a label **defined twice** is refused (`multiplyDefined`) rather than resolved to one of its records. And on either route, whatever the document class, **every label of a build that loaded `pgfpages`** is refused (`pgfpagesLayout`): a `\pgfpagesuselayout` (`resize to`, `2 on 1`) holds each page back until the next is built, so every label records a later page than its own, and the `/PageLabels` tree and the printed folios move with it. The evidence is the build's `.fls` or `.log` naming `pgfpages.sty` (or `pgfmorepages.sty`, which holds pages back the same way without loading it); the records show only that the file was opened, not that a layout is in use, so loading the package without `\pgfpagesuselayout`, or merely testing for it with `\IfFileExists{pgfpages.sty}`, is refused too, and the refusal says so. A label is refused as well when **neither** record could be read, or each was empty (`pgfpagesUnknown`), since whether a layout shifted the build then cannot be told; a compile always leaves a `.log`, so compiling again clears it. And when the `.log` holds no shipout mark while the PDF beside it has pages (`nothingShipped`) — it recorded a run that **shipped no page**, or is empty: a compile that stopped in the preamble rewrites the `.log` and `.fls` but leaves the earlier run's `.aux` and PDF, so those records describe the wrong run — every label is refused until the error is fixed and the document compiles again. Each of these whole-build refusals gives `pages: [N]` with the PDF's page count for the last page. To show the last page (`lastpage`'s `LastPage`, say), pass `pages:` with the page count, which the refusal names. Every refusal points at loading `hyperref`, or at finding the page with `extract_text`/`pdf_geometry` and passing `pages`. Read-only over the last build — it never compiles; run `compile` first. This is the tool for every question the log cannot answer: did a restructured column push the row onto a second page, do the columns end at comparable heights, is a figure panel clipped because its own PDF box is a few points too small (the page box comes back in `pageWidthPt`/`pageHeightPt`). `pages` selects 1-based page numbers (default: every page, at most **8** per call — the rest come back in `skippedPages`; an empty array is rejected rather than silently rendering nothing). `clip` crops to a rectangle given as **fractions of the page, origin top-left** (`{x0,y0,x1,y1}`), which matters as much as `pages`: on a poster or a wide figure the question is usually about one column, and a full page at legible resolution is a large image. Two sizing knobs: `maxEdgePx` (default **1600**) fits the _returned_ image to a token-sane size and is the right default for "is the layout broken"; `dpi` sets the resolution directly and **wins over `maxEdgePx`**, which is the precise path — clip one column, ask for 150 dpi. Both are bounded by a **4000 px** hard cap per edge, and a request that hits it comes back with `clamped: true` and the resolution actually used in `dpi`. Images are inlined up to a **5 MB budget on the base64-encoded payload**; past it the _tail_ of the range comes back as paths only (never a hole in the middle) and `note` says which pages and why. Pass `inline: false` for paths only. PNGs are written under the temp build dir, **never inside the project** — a `local` project is edited in place, not littered in place. That is not the whole truth about side effects, though: like `pdf_geometry` and `extract_text` it takes the per-project lock, because a peer session's `compile` rewrites the build dir in place, so it creates `<workspace>/.sessions/<project>/` if absent and can wait on — or time out against — a peer holding it. `rootFile` selects whose build is read: its own build-dir PDF (and `.aux`), in every workspace mode, so pass the root you compiled. Needs the optional native canvas backend (`@napi-rs/canvas`) — the **only** PDF tool that does — and it is never available in the Claude Desktop extension, where this tool refuses and says so (install from npm for page images); `doctor` reports which case you are in. The refusal comes before any PDF is opened, and it checks pdf.js first: a broken pdf.js install is reported as that, never as a missing canvas backend. A clipped or re-scaled render is written as `page-<n>-<hash>.png`, unique to the exact request, so two requests never overwrite each other. |
| `pdf_geometry`           | **Measure** the compiled page instead of eyeballing it. Read-only over the last build — it never compiles; run `compile` first. Returns boxes in **PostScript points (72pt = 1in), origin top-left** — the same convention as `render_pages`' `clip`, so the two compose: `render_pages` to look, `pdf_geometry` to compute. This is what answers "does this table's text overlap the figure frame above it, and by how many points", which no amount of staring at a PNG can. `kinds` picks what to report (default `["text", "images"]`): **`text`** is per-line boxes (pdf.js text items merged in their own frame — see the rotation note below — and by adjacency; the `text` on each box is the merged line's string, truncated to **160 characters** as a _label_ for the box rather than as content — use `extract_text` to READ a compiled page and `read_file`/`search_files` for the source). A text box spans **baseline to the font's declared ascent** — pdf.js exposes it as `styles[fontName].ascent`, a fraction of the em — and falls back to the full **em height** for a font that declares no usable one (`Symbol`/`ZapfDingbats` report `NaN`, an unembeddable font reports nothing at all, and a value outside `(0, 1]` is not believed). Under such a font the box is exactly what it always was: the fallback over-covers rather than guessing, because an under-sized box is the false negative this tool exists to avoid. Descenders (`g`, `p`, `y`) fall below the box either way — a descender touching a figure below still reads as clearance. Each box is built from the item's own text matrix, so **rotated text is handled**: a sideways table cell, a rotated axis label, and every line on a `pdflscape` landscape page (whose content is rotated inside the page _as well as_ the page carrying `/Rotate`) all get correct boxes. Page-level `/Rotate` and a non-zero MediaBox origin are handled too — every box maps through the page's own viewport transform, which is what makes the shared convention with `clip` true there. A rotated line of several items **is merged into one**: items are grouped in their own frame (shared direction and up axes to within a degree **and the same writing mode**, each origin projected onto the **running line's position axis** — the perpendicular to that line's advance axis, so what is compared is a candidate's perpendicular distance from that line's baseline rather than a coordinate in its own frame — and adjacency measured along that same line's **advance** axis), not by page-axis `y`. **Shear is modelled**: each box is built from the text matrix's own two column directions, so a slanted (non-orthogonal) matrix yields its true parallelogram rather than an orthogonal approximation. A **vertical** (CJK, `WMode 1`) line is merged too, not merely boxed: the column it sits in is read as the line position and the run down it as the advance, so a vertical line comes back as one column box rather than one box per item. Two neighbouring columns stay separate, and a vertical line is never merged with a horizontal one even where they share a coordinate. A line whose items drift in frame by up to a degree **is** merged wherever it sits on the page, and so is a genuinely **sheared** contiguous run, in either writing mode: the one-degree frame tolerance is the whole bound, with no hidden dependence on distance from the page origin; **`images`** is image and form XObject **placement rectangles**, i.e. what an `\includegraphics` figure occupies — and nothing else: general vector path geometry (`\fbox` rules, TikZ strokes) is **explicitly out of scope**, so a frame drawn purely with rules and no embedded image is not reported at all, and a form placement the walk could not bound comes back flagged `approximate: true` rather than passed off as a measurement. A box of either kind whose coordinates come out non-finite is dropped rather than reported. On the **image/form** path only, the walk additionally latches the refusal: a `cm` operand it could not compose leaves the last usable transform in place, and every box measured under it is flagged `unreliableCtm: true` rather than passed off as a measurement. The text path has no such latch — a non-finite item is dropped and the next one is unaffected — so a text box never carries the flag, and its absence there says nothing. Covers `paintImageXObject`, `paintImageMaskXObject`, `paintInlineImageXObject`, `paintSolidColorImageMask` and `paintFormXObjectBegin`; pdf.js's batched forms are **not** a gap, since they are produced only by its `QueueOptimizer` and reading an operator list selects the `NullOptimizer` instead. Still unreported: anything painted inside an **annotation appearance stream**, where pdf.js rebases the graphics state on a transform this walk does not model — those are counted per page in `annotationImagesSkipped`, a counted gap rather than a silent one; **`floats`** is opt-in and gives a `label -> printed page` index parsed from the build-dir `.aux` (cleveref's `@cref` shadow entries excluded — their "page" is not a page). A build whose records name `pgfpages` (its `.fls` or `.log` names `pgfpages.sty` or `pgfmorepages.sty`) comes back with `floatsPagesShifted: true` and a note: a `\pgfpagesuselayout` holds each page back a shipout, so every page in the index is likely one later than the label's own — find the page with `extract_text` rather than passing these to `render_pages`, whose `labels:` refuses such a build outright. When an `.aux` was read but **neither** record beside it could be, the flag stays absent (nothing shows the package) and the note says instead that the pages could not be checked against such a shift — `render_pages`' `labels:` refuses that build too. It is every `\newlabel`, **not only floats** — section and equation labels, `varioref`'s `@vr` records and `subcaption`'s `sub@` duplicates all appear, so match the key you want rather than assuming a row is a figure. It reflects the **last compile** — a label added since, or one whose reference has not converged (LaTeX's "may have changed, rerun"), is absent until the next one. Capped, each with its own count so a truncated answer is never silent (`floatsDropped` covers the rarer case of an entry found but unreportable — an over-long field, or a `\newlabel` group past the parser's scan budget, since the `.aux` is document-controlled and one entry must not be able to cost unbounded work; `floatsIndeterminate` is a third count, added to neither — a `\newlabel` marker whose own key group never closes, so there is no label to report and nothing to test for a cleveref shadow: a marker was there and nothing can be said about it; `floatsRefused` is `floatsDropped`'s opposite and is never added to it — `\newlabel`-shaped text found inside another entry's argument, or after a group that closes nowhere, declined rather than believed, so nothing is missing from the index because of it): **4** pages per call (lower than `render_pages`' 8 — a page of boxes is far more output than one PNG), **300** text lines and **100** image rects per page, **200** floats, and — separately from those count caps — a **20000-character budget on the JSON-encoded page boxes** and another on the **`floats` array** (`floatsOmittedBySize`), since every text label and `\label` key is document-controlled and a count cap alone is no bound on what the client receives. The box budget guarantees every page and kind an equal share and shares out what a sparse one leaves; each page's cut is a suffix (the first lines in drawing order are kept), counted per page in `textOmittedBySize`/`imagesOmittedBySize` and named in `note`. A dense two-column page comes back partial on a default call — ask for fewer pages or `kinds: ["text"]` alone to get more of each. Writes nothing into the project or its build directory — not even a temp file. ## Local (in-place) projects

Not every document lives behind a git remote. A `.tex` inside a repo of your own — a CV in your website
repo, notes in a scratch directory — is registered by **path** instead. Point at the directory, or just at
the document itself:

```jsonc
register_project { "project": "proposal", "path": "~/proposals/eurohpc.md" }
// -> registers ~/proposals, noting it was pointed at eurohpc.md
register_project { "project": "cv", "path": "~/site/cv/resume.tex" }
// -> registers ~/site/cv, with rootFile: resume.tex
```

A project is always a **directory** — that is the sandbox tools read and write within, and the unit
`compile` builds — so naming a file registers the folder around it. Every file in that folder becomes
readable and editable, so point at a document that sits in its own directory rather than one loose in your
home folder. Only a `.tex` is taken as the LaTeX `rootFile`; a markdown or plain-text document is not a
LaTeX root, and an explicit `rootFile` always wins.

Nothing is cloned and nothing is copied: `read_file`, `write_file`, `edit_file` and `compile` operate on
exactly those files, so what Claude compiles is what your editor has open. This matters because the
alternative — registering the surrounding repo as a git project to reach one file — clones the whole
repo, sees only committed state, and leaves you with **two copies of the document** drifting apart.

What holds for a local project:

- **The target must already exist.** The server points at it; it never creates a directory for you.
- **Nothing is written into it but your files.** Build artifacts go to a temp build dir, and the compiled
  PDF is surfaced into the workspace (`<workspace>/<id>.pdf`), never dropped beside your `.tex`.
- **Everything outside that directory is off limits** — the same sandbox as a clone, symlinks included:
  a `notes.tex` pointing at `~/.ssh/id_rsa` is refused, not followed. Registering a directory is not a
  statement about who put the links in it — it is very often a git working tree, and git stores a
  symlink as mode 120000, so a co-author can commit one and your next `pull` brings it in. If the links
  in that folder _are_ yours — one shared `refs.bib` or `figs/` linked into each paper — say so:
  `followSymlinks: true` on the project (`register_project`, `WEB_LATEX_MCP_PROJECTS`, or the registry
  file). Then reads, writes and `list_files` all follow them. Paths the server picks up on its own (a
  compile log, a synctex record) are refused whatever you set, since the document writes those.
- **Git tools do not apply.** `status`, `diff`, `commit`, `push`, `discard`, `revert`, `project_sync`,
  `reset_to_remote` and `read_file` with a `ref` all refuse with an explanation. There is no remote of
  ours, and the only repository around is _yours_ — the server will not commit to it, or read its
  history, on your behalf. Use your own git for that; the files are right where you left them.
- **The out-of-band-edit guard earns its keep here.** You have this file open in your editor, so
  `write_file`/`edit_file` refuse when the bytes changed since the server last read them (override with
  `overrideExternalChanges: true`).

> [!NOTE]
> Registering a local project points the server at a directory of your choosing, which it can then read
> and write. That is the feature, but it is worth being deliberate about which directory you name — as
> with any tool call, your client asks before the first one.

## Searching the project

`search_files` returns matching lines with their file and line number, so finding a phrase, a
`\label` or every use of a citation key does not mean reading each candidate file into context.
`contextLines` widens each hit; for a whole passage, use `read_file` with `startLine`/`endLine`.

The pattern is **literal by default**. `\Cref{tab:sota}` matches exactly that — in LaTeX the
common case is full of backslashes and braces, and a tool that read them as a regex by default
would quietly match the wrong thing.

### Why some regexes are refused

With `regex: true`, a pattern whose repeats can _trade input with each other_ past a fixed cost
estimate — a cubic or exponential blowup, or too long a run re-matched too often — is refused with
an explanation instead of being run:

```
.*a.*b                         refused — two repeats that can each match what follows them
(a+)+                          refused — a group repeated without bound
[^x]*a[^x]*a[^x]*b             refused — three of them, and not a `.` in sight
(fig|tab){2}                   refused — a group that can match more than one way, repeated by a count
.*a{999}b                      refused — a 999-character run matched again at every place `.*` can stop
.*\\label\{[^}]*\}             refused — `[^}]*` runs on from every `\label{` that `.*` can stop at
(?<=b.*a.*)                    refused — a lookbehind runs right to left: this is `.*a.*b` backwards
x{0,75}x*a*b*c*d*\}            refused — each `a*`, `b*`, … is entered at every split of `x{0,75}x*`
x{0,78}(\wx*)?\}               refused — `x*` inside an optional capture group costs a full step a character
x{0,30}x*a+a{11}b              refused — every split of `x{0,30}` ends where `x*` does, and `a+a{11}` runs after each
.*a?b                          accepted — one unbounded repeat, times two
[^a]*a{999}b                   accepted — the run cannot start inside what the repeat matches
.*\\includegraphics\[width     accepted — written-out text after one repeat
.*\\label\{fig:[a-z_]+\}       accepted — `:` stops `[a-z_]+`, so its runs never overlap
^.*TODO.*$                     accepted — anchored: tried at one starting position
\\section\{.*\\label\{[^}]*\}  accepted — costly only where a `\section{` starts
\\label\{.*\}\s*\\cite\{[^}]*\} accepted — `\s*` takes neither `}` nor `\`, so one `.*` stop per `\cite{`
.*\\label\{[a-z:_]+\}\s*$      accepted — each `.*` stop leads to its own `}`, so the `\s*` runs never overlap
\\cite(\[[^\]]*\])?\{[^}]*\}.*\\cite\{[^}]*\}  accepted — `[` or `{` next decides the optional, so it is no choice
```

**What bounds a regex search is the deadline, not this list.** A JavaScript regex match cannot be
interrupted from the thread running it — there is no point during `RegExp.exec` at which a
deadline can be checked — so the regex scan runs on a worker thread that is terminated at the
search's 5-second deadline. Whatever the pattern, a search ends there, and the server's own thread
is never blocked by it. The refusals are the first line of defence in front of that: they turn
away, before anything runs, the shapes whose backtracking blows up (all but one refused one above take
from a fifth of a second to minutes on a single 2000-character line), so an accepted pattern
normally finishes long before the deadline and does not come back as a partial answer just
because it was unlucky.

The refusals come from a cost model, and it is an estimate, not a proof:

- A group (or a backreference) is repeated more than once only if its body has exactly one
  fixed-width way to match — a bounded count does not make `(?:a|aa){0,40}` safe, it has
  Fibonacci-many ways to split forty characters. `(?:ab){2,5}` and `[ab]{0,40}` are fine. A group
  is never repeated without bound.
- Every _choice point_ — a repeat that can stop at more than one length (2000 lengths for an
  unbounded one, the line cap it runs against; `m - n + 1` for `{n,m}`; two for `?`), or an
  alternation more than one of whose branches can match at the same place — re-runs what follows
  it once per option, which matters when what follows can go on matching the characters it gave
  back. No piece may be re-run more than 4000 times per starting position: one unbounded repeat
  that overlaps what follows it, with room for a factor of two besides. Written-out text lowers
  that count: past `\label{`, which cannot overlap itself, `.*` reaches what follows at most once
  every seven characters; and a repeat right after text holding a letter it cannot match
  (`fig:` before `[a-z_]+`) cannot run over the next occurrence, so its runs never overlap. A
  `\b`, `^`, `$` or lookaround consumes nothing and does not interrupt the text around it
  (`[^}]*\bsmith\b` is limited by `smith` as `[^}]*smith` is), and a repeat that can take neither
  the letter before it nor the one after it (`\s*` in `.*\}\s*\\cite\{`) passes the limit on:
  `.*` then reaches what follows `\cite{` at most once per `\cite{`.
- Paths that _converge_ count too. In `x{0,30}x*a+a{11}b`, `a+` overlaps neither repeat before it,
  yet `x*` runs to the same place from each of the 31 places `x{0,30}` can stop, and `a+a{11}`
  then runs in full after every one of them: 1.1 to 2.7 seconds on one line, and two such
  stages (`x{0,30}x*\{y{0,30}y*\{a+a{4}b`) 4.4 to 6.4. So a piece that ends such runs, and
  everything after it, is counted as entered once per run. Brackets do not hide them: the count
  carries out of a group and into one, so `(x{0,30}x*\{)(y{0,30}y*\{)a+a{4}b` (about 3 seconds)
  and `x{0,40}(?:x*\{)a+a{9}b` (about 1.2) are refused like their flat spellings. A group that closes a bounded repeat before
  it counts that repeat once, as the written-out pattern does, so `\s?(\s*\\cite)(.*\\cite)` is
  accepted like `\s?\s*\\cite.*\\cite`; a group nested inside another can still cost acceptance
  (`(?:\s?(\s*\\cite))(.*\\cite)` is refused). Only a piece
  that _ends_ the runs counts them — one the repeat can still take lets them go on to end apart,
  so `[A-Z]{2,5}.*\\cite` and `\$\d{1,3}.*\$` are accepted (well under 20 milliseconds). The
  count is conservative: `\d{1,4}\w*:.*\\cite` is refused although it takes about 15
  milliseconds. Only a bounded repeat (a count, a `?`, an alternation)
  is counted this way: runs converging from an unbounded repeat's stops share the line with what
  follows them, and counting them refused ordinary searches like `\\cite\{[^}]*smith[^}]*\}.*$`
  (about a millisecond). The rewrite is usually to drop the bounded repeat — `x*` alone matches
  what `x{0,30}x*` does.
- A lookbehind is judged the way the engine runs it — right to left, last item first — so a
  `.*` written at its end is the first repeat tried, not a tail that cannot fail:
  `(?<=b.*a.*)` is `.*a.*b` run backwards and took 2 seconds on one line, and
  `(?<=b.*a.*.*)` over a minute. `(?<!\\)%` and `(?<=\\cite\{)[^}]*` are unaffected.
- A piece that can match nothing (`a*`, `,?`, `(b*)`) settles none of the repeats before it, so
  the engine stands at it once for every way those repeats can split the line — whether or not
  it overlaps them — and enters it each time. It is charged per arrival: after `x{0,75}x*`, four
  such pieces took 1.3-1.8 seconds and twenty-three took 8 to 10. What helps most is splitting
  the line fewer ways before it (`x*` rather than `x{0,75}x*`); making such a piece required
  (`\d+` rather than `\d*`) or merging several into one class (`[\s,;]*`) helps less, since
  that piece or what follows it is still entered once per split. An optional piece that must
  consume and cannot begin with what follows it (`(\[[^\]]*\])?\{`) is no choice at all — the
  next character decides it — and a fence carries through a repeat that is itself fenced, so
  in `.*\\label\{[a-z:_]+\}\s*$` the `\s*` runs from different `\label{`s never overlap.
- What each re-run costs counts too, weighted by what the engine actually spends: a counted run
  (`a{999}`, `(?:aa){700}`) or a backreference a full step per character, a plain `*`/`+` repeat
  a quarter — but a full step inside an optional or counted group that captures or can match
  nothing (`(\wx*)?`, `(?:x*)?`), where the engine saves and restores the group at every
  character given back — and a written-out letter a quarter — the engine checks written-out text several
  characters at a time, so `.*` followed by 400 written-out `a`s took 3ms where `.*a{400}b` took
  1.6s. The estimate per starting position may not exceed 40000 — one unbounded repeat followed
  by a counted run of nineteen characters, or about seventy-six written-out letters — and a
  pattern that can only be costly at a few starting positions (one that begins with `^`, or with
  written-out text) may spend the whole line's allowance at those. A trailing `.*` after which
  nothing can fail is reached once and is not re-run. `$` is something that can fail: a line
  can hold U+2028 or U+2029 (only `\n` and `\r` end one), which `.` does not match, and
  `.*TODO.*$` took 0.4 seconds on a line of `TODO`s ending in one — so `.*TODO.*` is accepted
  and `.*TODO.*$` is not. Anchored, `^.*TODO.*$` is tried at one position and is accepted.

Measured on one adversarial 2000-character line, against `\w*\w{19}!` as a reference (about
0.13 seconds on an idle machine), the costliest families of shapes these rules accept take 1 to 1.7
times the reference, and the slowest accepted patterns random and targeted searches have found take
2 to 3 times it (0.3 to 0.45 seconds, and over a second while the machine was running five such
searches at once) — so read those as ratios, not wall-clock promises, and as the worst found, not
a bound: a search over some 60000 generated patterns once found nothing slower than 2.6 times the
reference while the converging shapes above were still accepted at up to 54 times it. Ordinary LaTeX searches such as the accepted ones above take under 10 milliseconds. The
line is drawn by that estimate, not by how cost grows with the line: the cubic shapes tried at
every starting position, like `.*\\label\{[^}]*\}` (0.2 to 0.6 seconds), are refused, while a
cubic shape tried only where written-out text begins can fit — `\\cite\{[^}]*\}.*\\cite\{[^}]*\}`
(about 20 milliseconds at worst) is accepted, and its `\\ref` twin (about 30) is refused, 2% over,
for its shorter lead text. The rules are conservative on purpose: `(fig|tab){2}` is cheap in
practice and is refused anyway, and `\\hline.*&.*\\\\` is refused although its worst line took
about a tenth of a second.

The test is **character overlap** — whether a repeat can match the same characters as the thing
after it — not which metacharacters appear. That distinction is the whole rule:
`[^x]*a[^x]*a[^x]*b` contains no `.` at all and took 12 minutes on one line here, while
`\w+\s+\w+` chains three quantifiers and is linear. A rule written over syntax ("ban `.*`", "ban
chained quantifiers") would have let the first through and refused the second, which LaTeX
searches need. Overlap is judged over every character the pattern names, every code unit up to
U+0100 (whatever escape spells it — `\01`, `\47`, `[\c1]`) and the Unicode spaces `\s` covers,
so `\s` and `[^\x00-\x7f]` are correctly seen to share U+00A0; with `caseInsensitive`, over
every character that has another case as well, since `[ɐ-ɠ]` then also matches `Ɓ`.

Anchor each repeat to something it cannot match itself — `\Cref\{[^}]*\}` rather than
`\Cref\{.*\}` — and drop a leading or trailing `.*`. A match anywhere in the line counts, so
dropping it does not change which lines match — with one exception that favours dropping it:
under `excludeComments` a hit is judged commented by where it **starts**, and a leading `.*`
starts every hit at the beginning of the line, so `.*\\cite` reports `Some text % \cite{old}` as
a live hit where `\\cite` correctly calls it commented. Inside a lookaround the `.*` is part of
what is asserted, so there the advice is to bound it (`.{0,80}`) rather than drop it. A refusal
from the cost rules quotes the offending construct — with its position when two pieces are written
alike, as the two `a*` of `(?:a*)a*b` are — and suggests a rewrite, as does one for counted repeats
that multiply past the cap (lower a count); one for a construct the server cannot verify quotes it;
one for a pattern that is not a valid regular expression gives the reason and `regex: false` as the
way out; and a pattern over the 500-character limit — literal or not, since the limit applies to
every pattern — is refused with the suggestion to split the search into several calls.

### What is never silently missing

- **Assets are never searched**, whatever `filter` says, and come back under `skipped` — so "not
  searched" cannot be mistaken for "no match".
- **Output is budgeted** by rendered size — each match charged its JSON _and_ its lines in the text
  channel — with a match-count cap and an aggregate budget. Whatever was cut is counted
  (`omittedByCap`, `omittedBySize`) and the `note` names the cap that actually fired, never one
  that did not.
- **A search the deadline cut short says so.** `timedOut` is set, `filesNotReached` counts the files
  never opened, and a file cut off part-way is counted in `filesPartiallySearched` and named in
  `note` with how many of its lines were scanned — a match further down it was not looked for.
- `excludeComments` skips hits inside a LaTeX `%` comment, by backslash parity — `50\%` is live
  text, `\\%` starts a comment. It applies only to files where `%` _is_ a comment
  (`.tex`/`.sty`/`.cls`/`.bbl`/`.ltx`/`.latex`); every hit in any other searched file is reported,
  and `note` says how many such files there were rather than filtering nothing quietly. It has no notion of `verbatim`/`lstlisting`, where `%` is printed text; a hit there is
  reported as commented, so the option hides rather than rewrites — and the count it suppressed
  is always reported.

## Adding figures and new files

A figure that lives on your laptop but has never been in the project is what `add_asset` is for.
`write_file` takes text, so it cannot carry a PNG; `add_asset` copies raw bytes:

```
add_asset  project: paper
           path: figures/results.png
           sourcePath: ~/Desktop/results.png
```

`sourcePath` is an absolute path **on the machine running this server** (a leading `~` is expanded).
This is the cheap route: the bytes go straight from disk to the project without passing through the
model's context. For a client with no filesystem access, pass `contentBase64` instead — capped lower,
because those bytes are paid for per token.

The result reports the resolved source path and a sha256, so you can confirm the copy is
byte-identical to the file you meant. Missing parent directories are created by default, so
`figures/results.png` works before `figures/` exists.

**Both the destination and the source must be an asset type** (`.png`, `.jpg`, `.pdf`, `.eps`,
`.svg`, …). This is a security gate, not a convenience: `add_asset` is the one tool that reads a
file from outside every project sandbox, and the allowlist gates that read on BOTH sides — a
refused destination is what stops a project from ending up with a stray credential, and a refused
`sourcePath` is what stops the server from reading a credential file — `~/.ssh/id_rsa`, `.env`,
both non-asset — off disk in the first place. The source check runs on the realpath'd file, so a
symlink named like a figure cannot launder a non-asset target past it, and the destination is judged
on where it lands too — a link named `figures/x.png` whose target is not an asset type (a `.bib`, a
`.tex`) is refused. A `.tex` destination is
refused and points you at `write_file`; a `.bib` destination is refused and points you at
`add_citation`; a non-asset `sourcePath` is refused and points you at `contentBase64`.

New `.tex` files and folders need no special tool — `write_file` creates them, and `createDirs: true`
creates any missing parent directories along the way:

```
write_file project: paper
           path: sections/experiments/setup.tex
           content: \section{Setup}
           createDirs: true
```

Note that git does not track empty directories, so a folder only exists once it holds a file.

## Missing packages

A compile that fails because your TeX installation lacks a package reports it directly rather than
leaving you to parse the log:

```jsonc
{
  "success": false,
  "missingPackages": ["fontawesome"],
  "hint": "Missing from your local TeX installation: fontawesome. Install with your TeX distribution …",
}
```

Only `.sty` and `.cls` names appear there — a missing image or `.bbl` is a problem with the document, not
with the machine. Install it the way your distribution expects (`tlmgr install fontawesome`, or
`tlmgr --usermode install fontawesome` when you have no root) and compile again.

If that install fails, run [`doctor`](#tools): it reports whether the package manager can reach anything
at all. The common trap is an end-of-life TeX Live, whose `tlmgr` defaults to a frozen archive —
`tlmgr install` then fails in a way that looks like a network problem but is not:

```
warn distribution     TeX Live 2019/Debian — past end of life
warn package-manager  tlmgr revision 53568 — repository: https://…/historic/systems/texlive/2019/tlnet-final — (frozen archive)
ok   texmf-home       /home/you/texmf (writable)
ok   system-texmf     /usr/local/share/texmf (not writable — needs root)
```

The server never installs anything itself: it diagnoses and tells you the command to run.

## Registering a project from the chat

You don't have to set `WEB_LATEX_MCP_PROJECTS` up front — you can add a project mid-conversation just
by giving Claude its git URL (find an Overleaf URL under **Menu → Git**):

> 👽 Add my Overleaf project — the git URL is `https://git.overleaf.com/0123…`. Call it `thesis`.

Two tools register a project; they differ in whether the registration is remembered:

- **`register_project`** — persists the project to a `registry.json` in the workspace, so it is still
  there after you restart the client and is visible to any other session on the same machine. This is
  the recommended path, and the natural fit for **Claude Desktop**, where hand-editing the env config is
  awkward. It clones right away unless you pass `clone: false`. Re-registering the same id replaces its
  stored entry from the arguments given, and the result names any stored field that dropped.
- **`project_sync` with `gitUrl`** — a lightweight, **session-only** registration: it lives in this one
  server process and is gone on restart. Handy for a one-off; use `register_project` when you want it to
  stick.

The registry file stores only the id, git URL, and options (`rootFile` / `branch` / `username` /
`tokenEnv`) — **never a token**. A URL pasted with a secret in it has the secret removed before
anything is stored, echoed or cloned, and the result says what was removed and how to supply the
token instead: `https://user:token@host/…` keeps `user@` (a login name is not a secret, and your
credential helper may look the credential up by it — Azure DevOps and Bitbucket clone URLs carry
one), while a token pasted as the username (`https://ghp_…@github.com/…`) is removed whole. The token test
errs toward removal: a login name of 20 or more characters that holds a digit or mixes letter case, and
that the URL does not carry elsewhere in its host or path, is taken for a token and removed whole too. Credentials are still resolved per host at git time (see
[Configuration → Tokens](configuration.md#tokens--resolved-per-host)). Projects configured through
`WEB_LATEX_MCP_PROJECTS` always take precedence over a persisted entry with the same id.

The id becomes a directory name, so anything unsafe as one is refused — a path separator, a
character a Windows file name cannot hold, a leading `.` or `-`, a Windows device name, and a few
more — while Unicode letters, spaces and punctuation are fine: `thesis`, `paper-2026`, `thèse`,
`My Thesis`. Both tools refuse an id outside the rule (see
[Configuration → Project ids](configuration.md#project-ids) for all of it), and both refuse a
directory another project already uses.

## Citations via DBLP, Crossref or OpenAlex

References are added through a verified path, never hand-written. `.bib` files are **protected**:
`write_file`, `edit_file`, and `delete_file` refuse a `.bib` target unless you pass `confirmBibEdit: true`
— a guard so an agent can't quietly rewrite the bibliography. For writes and edits the guard looks
through symlinks: a `figures/x.png` that is a link to `refs.bib` is refused the same way (deleting
such a link only removes the link, so `delete_file` judges the name alone; a delete _under_ a linked directory removes the real file). The tool tells the agent to ask you first;
set the flag only after you approve a manual change (removing or fixing an entry).

To add a reference, use the two-step flow:

1. `search_references` queries an external bibliography — [DBLP](https://dblp.org/faq/How+to+use+the+dblp+search+API.html),
   [Crossref](https://api.crossref.org) or [OpenAlex](https://api.openalex.org) — and returns
   candidates, each with a namespaced record `key` (`dblp:conf/cvpr/HeZRS16`,
   `crossref:10.1109/CVPR.2016.90`, `openalex:W2194775991`). The result's `source` names the backend
   that answered; pass `source:` to pin one.
2. `add_citation` takes that key, **re-fetches the canonical BibTeX from that service server-side**,
   and appends it to the project's `.bib` (deduplicated by cite key — re-adding is a no-op). Because
   the entry text comes from the service and not the model, citations are verifiable rather than
   invented. With one `.bib` in the project it's chosen automatically; otherwise pass `bibFile`.

The key decides which service is asked, so a key always goes back to whoever issued it. OpenAlex
publishes no BibTeX of its own: an `openalex:` key is resolved to its DOI and the entry fetched from
Crossref (the result reports `via: "crossref"`), and a record with **no** DOI is refused rather than
assembled from metadata. Which backend runs, when one is substituted, and why the refusal exists are
covered in [Reference backend](configuration.md#reference-backend).

## Rewrite-preservation mode

Overleaf users commonly comment out the paragraph they are replacing rather than delete it, so the
old wording stays in the source next to the new one. `edit_file` can do this automatically on a
`.tex`/`.sty`/`.cls`/`.bbl`/`.latex`/`.ltx` file (case-insensitive) — commenting the original text
out with `% ` above the replacement, in place of deleting it — controlled by a project's **rewrite
mode**. This only happens for an edit that qualifies at all (see the line-alignment and `replaceAll`
restrictions below); an edit that doesn't qualify always applies the ordinary way, whatever the mode:

- **`off`** (default) — never preserve; the edit replaces the text as usual.
- **`prose`** — preserve only when the edit looks like a rewritten sentence or paragraph:
  the replaced text has at least 8 tokens (whitespace-separated, so a `\cite{…}` counts as one), most
  of them ordinary prose rather than LaTeX markup, and the replacement isn't nearly identical to the
  original. A typo fix, a changed number, a swapped `\cite` key, or a renamed `\label` are treated as
  minor edits and are not preserved. `edit_file`'s result names the resolved mode as `rewriteMode` and
  how many of the call's edits were preserved as `preservedEdits`.
- **`always`** — preserve every edit that qualifies (see below) on an applicable file. This is not
  "regardless of shape": a mid-line match or a `replaceAll` edit is never preserved, whatever the
  mode.

It never applies to `write_file` (a whole-file overwrite has no single old paragraph to comment out
above the new one — commenting out the entire previous file is not what preserving a rewrite means)
or to a `.bib` file (already governed by its own `confirmBibEdit` guard). On any other extension the
mode is inert, and the edit is applied unchanged. Both checks judge the link-resolved name as well as
the one you gave, the way the `.bib` guard does: editing through an in-project symlink changes its
target, so a `notes.tex` link onto `body.md` or `refs.bib` preserves nothing.

**Known limitation: verbatim-like environments.** Whether a file uses `%` for comments is decided by
its extension, not by where in the file the edit lands. Inside `verbatim`, `lstlisting`, `minted` and
friends, `%` is _not_ a comment — so a preservation landing there becomes a visible line in the
compiled PDF rather than a hidden one. Detecting the enclosing environment reliably would take real
LaTeX parsing, so this is accepted rather than guarded: the cost is one stray visible line, under a
mode you opted into, which shows up the first time you compile. If you are rewriting a code listing,
pass `preserveOriginal: false` for that call.

**Setting it.** `set_rewrite_mode({ project, mode })` changes a project's sticky mode, persisted
per-project so every session sees it; call it with `mode` omitted to read the current effective mode
without changing anything. A per-call `preserveOriginal: true`/`false` on `edit_file` always wins over
the project's stored mode, in both directions — force it on for one particularly important rewrite, or
off for a mechanical one. This overrides the mode, not eligibility: on a `.bib` file or a file without
`%`-line-comment syntax the result still reports `rewriteMode: "off"` and nothing is preserved (the
result text says so); on an eligible file a mid-line match or a `replaceAll` edit still reports the
resolved mode with `preservedEdits: 0`. Resolution order: `preserveOriginal` (this call), then the project's stored
mode, then `WEB_LATEX_MCP_REWRITE_MODE` (the server's default), then `off`. See
[`WEB_LATEX_MCP_REWRITE_MODE`](configuration.md#environment-variables) to change the default; read
`list_projects` for a project's effective mode and `server_info` for the server-wide default only
(not necessarily what any given project uses). To get the Overleaf
habit back, set the mode to `prose` (or `always`) — per project with `set_rewrite_mode`, or
server-wide with `WEB_LATEX_MCP_REWRITE_MODE`.

The preserved block is never marked — it looks exactly like a paragraph a human commented out on
Overleaf, with no sentinel. `arxiv-clean-project` already strips comments before submission, so this
never needs undoing programmatically.

**Preservation requires a line-aligned match, and never applies to `replaceAll`.** An edit is only
ever preserved when `oldString` starts at the beginning of a line and ends at the end of a line in
the file as the call found it — or in the current content, for a match inside text an earlier edit
of the same call inserted — and its end must hold in the current content too, since an earlier edit
that took its terminator leaves live text right after it. It ends a line either because a line
terminator (or end of file) immediately follows the match, or because `oldString` itself already ends with one (a caller can include the trailing
newline in what it wants replaced or deleted). A mid-line match has nowhere safe to put a
`%`-comment (a mid-line deletion would swallow the rest of that line into the comment; a mid-line
replacement would reflow trailing text onto the replacement's line). And an edit with
`replaceAll: true` is never preserved at all, since there is no single match position to comment
above it — it always applies unchanged. Neither case counts toward `preservedEdits`. A
**line-range** edit (`startLine`/`endLine`) is whole lines by construction, so it is always
eligible: every line it names is commented out — a blank line included — and each keeps the
terminator it had, so a CR-only or CRLF file stays that way.

**A preservation leaves the old text in the file as a comment.** Every line of it is prefixed with
`% `, so a multi-line `oldString` no longer occurs verbatim — but any single line of it does, as
`% <that line>`. A later `edit_file` call whose `oldString` still occurs in that comment will match
it: if the text also still occurs live, the call is refused as non-unique (add more surrounding
context); if the earlier rewrite replaced the live copy, the comment is now the only match and the
edit is applied to it — rewriting text no reader sees, and reporting success. Only within a single
call does the server catch that (below). Across calls, include enough surrounding context, or a line
the rewrite kept, so `oldString` lands on live text.

Within a **single** call it is stricter, because there the comment is one the server just created
rather than one you can see: when a later edit in the same `edits` array matches inside (or across
the edge of) a block an earlier edit in that array preserved, `edit_file` refuses it outright —
`Edit N: oldString only matches text preserved (commented out) by an earlier edit in this same call,
not the live document; the live occurrence was already replaced by that edit.`
That edit's live target was already replaced by the earlier edit, so applying it would silently rewrite
dead commented-out text and report success for a change no reader ever sees. The whole call fails and
the file is left untouched; re-issue the edits against the text as it now stands. A `replaceAll` edit
is exempt from that match check, since rewriting the comment along with the live text is its
documented behaviour — but a `replaceAll` that rewrites a block's own end must still leave the comment
line ending in its replacement text. The same call is also refused when a later edit would take the
line break that ends a block an earlier edit preserved (`Edit N removes the line break that ends the
text edit M preserved (commented out) in this same call, …`), since the text after it would continue
on the comment line, where LaTeX drops it; and when a deletion would leave a line break right after a
preserved block that ends in a bare carriage return (the two read as one CRLF and swallow a blank
line). Make such edits in separate calls.

## References in any format

A bibliography is not always a `.bib`, and a document is not always on a remote. A proposal drafted in
markdown carries its reference list as a numbered section; a paper without a `.bib` carries a LaTeX
`thebibliography`. `list_references` reads all three and reports which one each entry came from, so a
caller knows how far to trust the parsed fields:

| `format`  | Source                                      | Fields                                                             |
| --------- | ------------------------------------------- | ------------------------------------------------------------------ |
| `bibtex`  | A `.bib` (`@string` venue macros resolved)  | Exact.                                                             |
| `bibitem` | `\bibitem{key} …` in a `.tex`               | Key exact; the description is free text, so fields are a hint.     |
| `prose`   | A reference list in `.md` / `.txt` / `.rst` | Heuristic — `raw` is the ground truth, unless `rawOmitted` cut it. |

Prose parsing errs towards under-claiming: a `title` is only filled in when the text delimits it
(quotes, emphasis), and authors only when a parenthesized year separates them from the rest. A field
left empty means "the text didn't say", not "the reference is missing it" — and `raw` carries the
entry verbatim, which is what settles a doubtful field. Since #147 `raw` is budgeted too, so an
over-long one keeps a verbatim prefix and ends in a `… [+N characters omitted]` marker; that entry's
`rawOmitted` is what tells you the ground truth was cut, and re-reading the file is what gets it
back.

`check_citations` then does the cross-reference — the regex diff you would otherwise write by hand:

```jsonc
// check_citations { project: "proposal" }
{
  "undefinedCitations": [{ "key": "ghost2030", "uses": [{ "path": "proposal.md", "line": 4 }] }],
  "uncitedEntries": [{ "key": "never2019cited", "path": "ref.bib", "line": 17 }],
  "duplicateKeys": [],
  "incompleteEntries": [{ "key": "cabon2020virtual", "missing": ["journal|journaltitle"] }],
}
```

Both are read-only and neither touches git, so they work on a [local project](#local-in-place-projects)
with no remote at all. The [`/verify-citations` skill](skills.md) drives them, then checks each entry
against DBLP, Crossref or OpenAlex.

### A bibliography in another project

A draft often does not carry the bibliography it cites: a proposal in one folder, the group's shared
`ref.bib` in an Overleaf project. `bibliographyProject` names the project the entries live in, and the
cross-check happens in one call:

```jsonc
// check_citations { project: "proposal", bibliographyProject: "shared-bib" }
{
  "bibliographySources": ["ref.bib"], // paths relative to "shared-bib"
  "bibliographyProject": "shared-bib",
  "entryCount": 312,
  "undefinedCitations": [{ "key": "ghost2030", "uses": [{ "path": "proposal.md", "line": 4 }] }],
  "uncitedEntries": [], // see below
}
```

Two things about it are deliberate:

- **Each path stays sandboxed in its own project.** `documents` resolve inside `project`,
  `bibliography` inside `bibliographyProject`. Nothing crosses over, and the parameter takes a
  **project id**, not a `"project:path"` string — you reach another project only by naming one you
  registered, never by writing a path that walks out of this one. Reading is all it does: writing across
  projects (`add_citation` into someone else's `.bib`) stays a separate, deliberate act in that project.
- **The findings cover only what your draft cites.** A shared bibliography is _meant_ to hold hundreds of
  entries this draft does not use, so `uncitedEntries` comes back empty and `duplicateKeys` /
  `incompleteEntries` are limited to cited keys — `entryCount` still tells you how big it is. To audit
  the shared bibliography as a whole, run `check_citations` with `project: "shared-bib"` instead.

`undefinedCitations` is the answer you came for: keys the draft cites that the shared bibliography does
not define. Each one has to be added **there** — `add_citation { project: "shared-bib", … }`, from a
`search_references` result, with that project's permission.

`list_references` has no equivalent parameter and needs none: it already reads whichever project
`project` names, so listing another project's references is just `list_references { project:
"shared-bib", filter: "…" }`. Only `check_citations` joins two sets, so only it names two projects.

## Shell escape (for TikZ externalization)

Documents that use TikZ externalization (`\usetikzlibrary{external}` + `\tikzexternalize`) compile each
picture in a separate sub-process, which needs TeX's system-call (`\write18`) mechanism. That is disabled
by default, so `compile` exposes two opt-in flags:

- **`restrictedShellEscape: true`** (preferred) — passes `-shell-restricted`, permitting only the helper
  binaries on TeX's allow-list. Safer, and sufficient for many externalization setups.
- **`shellEscape: true`** — passes `-shell-escape`, letting the document run **arbitrary** shell commands
  during compilation.

> ⚠️ **Security.** `-shell-escape` lets a `.tex` file execute arbitrary commands, and the document comes
> from a shared remote others can write to. Both flags default to `false`, are **never** inferred from
> document contents, and a failed compile is **never** silently retried with them enabled. When a compile
> fails only because system calls were disabled, the result carries a `hint` (and collapses the repeated
> per-figure `Package tikz Error`s into one diagnostic) so you can decide whether to re-run with a flag.
> Enable shell escape only for a project you trust; try `restrictedShellEscape` before `shellEscape`.

Independently of the flags, `compile` mirrors the project's subdirectory structure into its build
directory, so a document that writes to a relative path (like externalization's `imgs/` cache) no longer
dies with `I can't write on file`.

## Out-of-band edits

Because clones are ordinary git working trees — and, with [workspace-local clones](configuration.md#workspace-local-clones),
sit right in your editor — you may edit a `.tex` file directly while the agent is working. The server
guards against silently clobbering those edits, the same way `push` refuses when the remote moved:

- The server remembers the content of each file **it gave you in full** — `read_file`, and
  `list_references`, but only for a bibliography whose bytes it returned whole: since its entries can
  be paged by `maxResults` or cut by a budget, it claims a file only when every entry of that file
  shipped with nothing omitted (#171), every one is a BibTeX entry, and their `raw` text covers the
  file apart from whitespace — so a `thebibliography`, a prose reference list, or a `.bib` holding
  `@string`/`@comment` blocks or `%` comments is never claimed — along with everything it writes. Other reads
  do not count, even when some of their bytes reach you: finding the root file to compile, fetching the
  five lines around a compile error or a PDF comment, or scanning your documents to answer a question
  about them (`check_citations` returns cite keys and line numbers, not content). None of those is
  something an edit could be based on, and treating them as if they were would let a later write clobber
  your edits believing they had already been read. Before `write_file`, `edit_file`,
  or `delete_file` touches a file, it re-checks the bytes on disk. If they changed since the server last
  saw them, the tool **refuses** with a message telling the agent to re-read first. Re-reading
  acknowledges your version and lets the next write through; passing `overrideExternalChanges: true`
  deliberately overwrites your on-disk changes.
- `status` reports an `externalChanges` list — files modified on disk directly rather than through the
  tools this session — so the agent can acknowledge your edits before building on them.
- Baselines reset after `project_sync` and `discard`, since those legitimately rewrite the working tree.

The guard is per session and in-memory; it complements git rather than replacing it (`diff` still shows
exactly what changed).

## Parallel sessions

One person can run several agent sessions on the same paper — one per section — each a separate server
process over the same clone. Name each with `WEB_LATEX_MCP_SESSION` (see
[Configuration](configuration.md#parallel-sessions)); the tools then behave as follows.

- **`commit` is session-scoped by default.** It commits only the edits _this_ session made, staging
  them directly rather than running `git add`, so a peer's half-written paragraph in the same file
  stays uncommitted on disk. The result carries `scope`, `session`, and `leftUncommitted` (what was
  deliberately not taken — a file can appear there even when the commit included part of it). Pass
  `scope: "all"` to commit the whole working tree instead, other sessions' work included. When this
  session tracks nothing of its own, an unscoped `commit` falls back to the whole tree only if no
  other live session shares the clone; with one it refuses and commits nothing, so taking a peer's
  work is always a `scope` you passed. "Tracks nothing" is judged when the call begins: a session
  whose last change the call's own refresh settles (undone by hand, or already in HEAD) is told there
  is nothing to commit, never widened to the whole tree.
- **`commit scope: "paths"` commits exactly the files you name.** For work that reached the clone
  without going through `edit_file` / `write_file` — a script's output, the client's own file tools —
  which no session owns, so a session-scoped commit cannot see it. It requires a non-empty `paths`,
  stages only those paths (a directory covers what is under it), and refuses a path a live session's
  shadow lists rather than taking that session's in-flight lines — `scope: "all"` remains the
  deliberate way to do that. Where `scope: "all"` + `paths` widens silently to the whole tree when the
  list is empty, `"paths"` cannot.
- **`status` says who owns what, and how fresh it is.** `sessionChanges` / `otherChanges` split the
  uncommitted files, `conflictedChanges` names files this session can no longer commit, and
  `activeSessions` lists the other sessions with whether they are live, the paths their shadow holds
  (`changes`, `null` when that session's index cannot be read), and their last write through this
  server (`lastWriteAt`). Edits a session makes outside the server leave no trace here. Sessions
  that have exited, have been quiet for hours, **and** whose shadow index records no changes are not
  listed individually — they are counted in
  `staleSessions`, because a record is deleted only on a clean shutdown and a killed agent process
  leaves one behind forever. That count says their index recorded nothing, not that they changed
  nothing: an empty index cannot be told apart from an index whose write failed, so a session that
  went quiet only recently stays listed — it may be the author of dirty lines in `otherChanges` that
  nothing else accounts for. A session whose index cannot be read is never counted there: unreadable
  is not "owns nothing", so it stays listed with `changes: null`. Nothing is deleted from disk —
  `status` takes no lock, and reaping a record while its session is still recording would destroy
  the ownership proof `commit scope: "paths"` and `push` refuse on. For the same reason `status`
  writes nothing to any session's records beyond its own heartbeat: it reports this session's
  changes as they stand on the current HEAD
  without persisting that view, which the next locked `commit`/`push`/`project_sync` does.
- **`push` waits for live peers, and says who is mid-edit.** A push has to rebase, and a rebase needs
  a clean tree — so it refuses while another live session exists and the tree holds work that is not
  this session's. The refusal attributes each such file: which live session's shadow owns it, that
  session's last write age and heartbeat age, and which files no live session owns (edited outside the
  server, or left by an exited session). A 30-second-old write means wait; a two-hour-old one is a
  judgement call, made with `commit scope: "all"` or `"paths"` deliberately. A session whose index
  cannot be read is treated as owning every listed file. A file this session edited is disputed
  too when a live peer's shadow also lists it (or a live peer's index cannot be read): the refusal
  says it carries this session's edits as well — land those with `commit` (default scope), then
  push without a `message` once the owner has committed, since a `message` commits the whole tree,
  the peer's lines included.
  Once past that peer guard, untracked files never block it, whoever left them. Modified tracked
  files that no live session owns are refused by name too, because git cannot rebase over them —
  resolve with `commit` (this session's edits by default, `scope: "paths"` for named files,
  `scope: "all"` for the whole tree), a `message` on push (which commits the whole tree), or
  `discard`. And an untracked file the incoming commit would add is refused by name, with the clone
  left intact; the refusal prescribes `commit scope: "paths"` with exactly those paths, so a peer's
  in-flight work is not swept up on the way to a proper conflict.
- **Same-line collisions are surfaced, never guessed.** If this session and someone else changed the
  same lines, the file is flagged and excluded from commits, and stays flagged. `commit`'s result
  lists every excluded file in `conflicted`; `unrecorded` (a subset of `conflicted`) separates out
  files excluded because this session's own record of its change failed rather than a collision — a
  distinction the result text also spells out when both kinds are present in the same commit. The two
  ways out are `commit scope: "all"` (take the working tree as it stands) or `discard` (give up this
  session's version). Taking it settles it — and if the working tree already matches HEAD for the file
  (a `push` with `message` committed it, or a hand revert), `scope: "all"` or `scope: "paths"` naming
  it settles the record without a commit: the result carries `committed: false` and the file under
  `settled`, instead of refusing with nothing to commit.
- **Ignored files are never committed, by any scope.** A session commit stages from the session's
  shadow rather than through `git add`, which used to let a file git ignores (`.gitignore`,
  `.git/info/exclude` — the local note `summarize-paper` keeps out of git that way) into a commit and
  a push. `commit` now asks git which of the session's files are ignored, skips them, lists them under
  `ignored`, and drops them from the session's record; a tracked file that happens to match an
  ignore pattern still commits, as it would under `git add`. "Tracked" follows the scope: the
  session scope and `scope: "paths"` reset the index to HEAD before staging, so there it means
  tracked at HEAD (a hand `git rm --cached` changes nothing); `scope: "all"` with `paths` stages
  over the index as it stands, so there it means tracked in the index.

Mutating operations are serialised across processes with a lock file, so two servers never rewrite the
clone's index at once. Three read-only tools take that same lock — `render_pages`, `pdf_geometry` and `extract_text` —
because they read the temp build dir that a peer's `compile` can rewrite mid-read; any of them can therefore
wait on, or time out against, a peer holding it. The model, and what it deliberately does not do, is in [Parallel sessions on one
clone](CONCURRENCY.md#parallel-sessions-on-one-clone).

## Reviewing a whole session

`diff` with no `ref` shows uncommitted work — which goes blank the moment you commit, and the workflow
encourages committing several times in a session. Pass `ref` to diff the working tree against a commit
instead:

- `ref: "HEAD~3"` — everything since three commits ago, uncommitted edits included.
- `ref: "<sha>"` — since a commit you noted at the start of the session (`commit` returns its sha).
- `ref: "origin/master"` — what this branch has that the remote does not. (`push` reports the other
  direction, `remoteCommits`, and `status` reports `aheadCommits`.)
- `ref: "HEAD~3..HEAD~1"` — a two-dot range, when you want two commits compared and not the working tree.
- `ref: "<hash>~1..<hash>"` — one commit's full diff, e.g. a remote "Update on Overleaf." commit reported
  by `push`'s `rebasedOver` or `status`'s `behindCommits`, each of which now lists the commit's files with
  line counts.

`path` still narrows it to one file. `ref` and `staged` are contradictory and are rejected together
rather than one silently winning, and an unresolvable ref is reported by name instead of surfacing a raw
git error.

**On a shared clone this is not session-scoped.** `commit` takes only your own edits, but the history a
ref reaches into is everyone's — so `diff` against `HEAD~3` on a clone with several sessions shows peers'
commits alongside yours. It answers _what changed in this file_, not _what did I change_. For the latter,
diff against the sha your own last `commit` returned, or use `status`, whose `sessionChanges` /
`otherChanges` split is session-aware.

## Undoing a commit

`discard` reverts _uncommitted_ changes to HEAD — it cannot reach past it. To walk back a change that
has already been committed (and possibly pushed), use `revert`:

```
revert(commits: ["<sha>"], confirm: true, expectRef: "<sha>~1")
```

It runs `git revert --no-commit` and then unstages, so the undo lands **in the working tree only** —
review it with `diff`, then land it with `commit`. Nothing is committed for you, deliberately: it is
the same two-step separation `commit` and `push` already enforce, and it leaves the revert's message
in your hands. (There is no `commit: true` shortcut for that reason.)

**`matchesRef` is the point of the tool.** Pass `expectRef` — normally the commit before the one you
are reverting — and the result tells you whether the reverted files now equal it. That is the
difference between "I ran a revert" and "the revert is exact", and it is not something `diff` can
answer: `diff` returns a unified diff for a human to read, not an assertion you can branch on. The
comparison covers the **reverted paths only**, so a collaborating session's unrelated dirty file
cannot make an exact revert report `false`; when it _is_ `false`, `mismatchedFiles` names what
differs and by how much, so the answer is actionable.

**What it refuses, before writing anything.** A merge commit (it takes no mainline parameter — revert
it with your own git); a path that is a symlink on either side or that lies under a linked directory
(a revert writing through a link would write outside the project, so it refuses rather than follows);
a `.bib` bibliography unless you pass `confirmBibEdit: true`, as for `write_file` and `edit_file`; and
a touched file with uncommitted changes — which is what keeps a revert off another session's
in-flight work, and what lets the abort below be exact. Commit or discard those first.

It also refuses while **anything is staged anywhere in the clone**, which looks stricter than it is.
Aborting a conflicted revert means `git revert --abort`, and that resets the _whole_ index: a
collaborator's `git add`ed file on a path the revert never touches would come back at HEAD with its
staged work gone. The check has to happen before the revert starts, since by the time a conflict is
known that loss is already unavoidable. Commit the staged work, or unstage it with `git reset`.

**A conflicting revert aborts.** If the change has been written over since, the revert stops and puts
the clone back exactly as it was: no `<<<<<<<` markers anywhere, nothing partly applied, and any
unrelated uncommitted work untouched. You get `status: "conflict"` with `conflictPaths` and the two
refs to read each side from — `read_file(path, ref)` with `oursRef` for what is there now and
`theirsRef` for what the revert wanted to restore. That is deliberately lighter than `push`'s
conflict payload: because the abort loses nothing and both sides stay readable at a ref, there is no
content to return and nothing that needs budgeting.

**On a shared clone.** The reverted lines become _your_ session's changes — a following `commit` with
its default session scope lands exactly the revert. Any other session's record of those same files is
settled at the same time, so a peer cannot later commit its pre-revert copy over your undo.

## Reviewable, safe pushes

`commit` and `push` are separate, and nothing pushes automatically. Review with `status` / `diff`,
`commit` locally, then `push` with `confirm: true`. Because people may also be editing in the Overleaf
web editor, `push` is **safe by default**: it `pull --rebase`s onto the latest remote (immediately before
pushing) and **never force-pushes**. A rebase conflict means the agent and a human touched the same lines —
`push` aborts the rebase and returns `status: "conflict"` — a per-file 3-way payload: each conflicted
file's `base`/`ours`/`theirs` plus a marker `hunks` view, and top-level `conflictPaths` (every conflicted
path, never capped), `remoteHead`, `mergeBase`, and `remoteCommits`. (You can read any side directly with
`read_file(path, ref)` — `ref` takes `remoteHead`/`mergeBase` or any commit sha.) By default
(`conflictDetail: "auto"`) the per-file payload is **budgeted** to fit in one tool result: `hunks` are
allocated first (least recoverable once the rebase aborts), then `base`/`ours`/`theirs`, each capped
individually — a part that doesn't fit comes back `null` with a matching `elided` entry (its true size and
a `read_file(path, ref)` pointer to fetch it in full; an elided `hunks` block has no `ref` of its own —
it carries its hunk `count` and the first 20 line `spans`; reconstruct it from the fetched sides) — and a `null` with **no** `elided` entry still means the ordinary
thing, absent on that side (added/deleted). Past 20 conflicted files the rest get no per-file detail at
all, though they remain fully named in `conflictPaths`. `conflictTruncated` is true whenever any of that
fired. Pass `conflictDetail: "full"` for the old, uncapped behavior — every side of every file in full,
no file limit, every remote commit — when you want the complete payload and can take the size. By default
`remoteCommits` is capped too (20 commits of 5 files each, `remoteCommitsOmitted` / per-commit `filesOmitted`
saying what was cut); `status.behindCommits` lists them all, since the clone is back at its pre-push state. It
never auto-merges. To resolve, retry `push` with a `resolutions` array — the full merged content for each
conflicted file (`.bib` files need `confirmBibEdit: true`); the set is validated (missing/extra files are
named; a path that is a symlink on our or their side of the conflict is refused outright, since content
cannot resolve a link — resolve that one by hand and push again; a link both sides already replaced with
a file is an ordinary content conflict and resolves normally), an optional `expectedRemoteHead` refuses the push if the remote moved again (a commit SHA — the
`remoteHead` the conflict reported, abbreviated to no fewer than 4 hex characters if you like; a ref
name such as `origin/master` is refused, since it pins nothing), and success returns `pushedSha`. If the remote instead just keeps moving — a collaborator's
push landing in the gap between fetch and push — the pull-rebase is retried automatically (up to 3
rounds); losing every round returns `status: "remote-moved"` with nothing pushed and the clone intact —
re-run `push`. **That retry does not apply when `expectedRemoteHead` was given**: pinning it means you
asked to be refused rather than have your merge silently rebased over a second remote move, so it is one
round only — a lost race is reported straight away as `status: "remote-moved"`, nothing pushed. The
(budgeted, by default) conflict payload is delivered in the result **text** too
(not only `structuredContent`), so a client that drops structured fields can still resolve. A successful
`direct` push also reports `rebasedOver` — the remote commits that landed underneath your change. For
larger edits, `mode: "branch"` commits to a local review branch and returns its diff, landing it only on
`approve: true`. See [`CONCURRENCY.md`](CONCURRENCY.md) for the full model.
